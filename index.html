01 / The problem

AI made individuals faster. It did not change how work flows.

Ask what it changed about how long work takes to reach done. The honest answer is usually "not much".

01

Re-reading the request

Every item of work is digested from scratch. The description, the attachments, the comments, the two chat threads. Nothing carries over from whoever last handled something similar.

02

Rediscovering the context

The same lookups, the same systems, the same conventions, once per item per person forever. The knowledge exists in the organisation, just nowhere the next piece of work can reach it.

03

Confident wrong answers

An assistant proposes a fix to a file that does not exist, or a helper with a different signature. Nothing checks the plan before someone builds on it.

04

Evidence built from memory

What was tested, what was skipped, what is still risky, reconstructed at review time and thinner than anyone likes to admit.

With an assistant TODAY

Ticket arrives→ A person reads it→ A person greps
assistant drafts→ A person checks→ A person ships

One step got faster. Five did not, and all of them still queue behind the same person. Nothing was written down for the next run.

With Sequent WHAT WE BUILD

Ticket arrives→ agents investigate→ YOU DECIDE
agents implement→ agents verify→ YOU DECIDE

A person is still accountable, at the two moments where judgement changes the outcome. Everything either side carries itself and leaves a record behind.

None of that is a model problem. It is a process problem. There is no structure that makes findings persist, no stage whose job is to attack the plan, and no record that survives the terminal being closed.

02 / How it works

One command. A staged pipeline. Four gates.

Sequent installs into your repository as agent definitions and slash commands. No service to run, no dashboard to log into. It lives where your engineers already work.

  1. Intake

    Fetches the ticket from Jira exactly once, classifies it, opens a run record on disk.

    lead

  2. Analysis

    Greps before it concludes. Every claim cites a file and a line, and it names what is already correct nearby.

    analyst

  3. Architecture

    Features only. Cuts work into waves where no two tasks touch the same file.

    architect

  4. Challenge

    Tries to disprove the analysis. Re-opens every cited path, greps the pattern independently, reports what it could not verify.

    challenger
  5. ◼ Gate 1 / Plan

    Blocks every edit to a source file. You see the root cause, the plan, and everything the challenger could not prove.

  6. Implementation

    The approved plan and nothing else. Anything else it notices is written down, not fixed.

    developer
  7. ◼ Gate 2 / Implementation

    Blocks the QA stage. The diff plus a self check against the plan. Scope drift surfaces here, not at review.

  8. QA

    For a bug, the regression test is written first and proven to fail against the unfixed code.

    tester

  9. Review and security, in parallel

    Same diff, different files written. One reads it hunk by hunk, the other hunts injection, authz, secrets and bulk data paths.

    reviewer / security
  10. ◼ Gate 3 / QA

    Blocks the delivery gate. You accept the evidence and the residual risk, not the claim that it passed.

  11. Docs

    Finds documentation the change just made false. Drafts the release note and the PR body.

    docs
  12. ◼ Gate 4 / Delivery

    Blocks every outward facing action. The exact branch, commit message, PR body and Jira comment, shown before any of it happens.

  13. Release

    Branch, commit, push, pull request, Jira comment. Never a merge, never a force push.

    release

  14. Retro

    What the plan got wrong, where the run stalled, and concrete edits to propose to the agent definitions.

    retro
The rule underneath

Nothing is asserted that was not read

Every claim in a Sequent artifact names the file and line it came from. An agent that cannot find something says so, and the challenger checks. A truthful "I could not verify this" is a better outcome than a plausible guess, because at a gate a human can act on the first and cannot act on the second.

      04 / Where it applies
      
      Software delivery is one shape. It is not the only one.
      
      
      
        A queue, a decision needing judgement, a handoff, an outcome somebody must justify later. Most operational work looks like that.
      
      
    
      

    
      
      
      
        01
        
      It arrives as a request
      
        
      A ticket, a form, an email, a case, a claim, a row in a queue. Something enters with context attached and somebody has to read it properly before anything sensible happens.
      
      
      
      
      
        02
        
      It needs judgement, then work
      
        
      Someone decides what this actually is, what it touches and what could go wrong. Then the work itself follows from that decision, and doing it before the decision is how rework happens.
      
      
      
      
      
        03
        
      Somebody is accountable for the outcome
      
        
      A person signs it off, and later has to explain why it was reasonable. That is the requirement most automation ignores, and it is the reason the approvals and the record exist.
      
      
      
    
      

    
      
      
      
        
      
          
      What changes between workflows
      
          
      
            The specialists change, because they are shaped around your process rather than ours.
            The systems they reach into change, because they are yours. What the approvals gate
            changes, because your risk is not somebody else's.
          
      
          
      
            What does not change is the structure: read it once, work out what it really is,
            have that challenged before anybody builds on it, do the work, prove it, and stop
            for a person at every consequential step.
          
      
        
      
        
      
          
      How we decide whether it fits
      
          
      
            That is the diagnostic week, and it is deliberately the first thing we sell. We map
            how work actually moves through your organisation, find where it waits, repeats,
            drifts or breaks, and tell you which workflow has the most to gain.
          
      
          
      
            Sometimes the answer is that a workflow should not be automated at all, or not yet.
            We would rather say that in week one than build the wrong thing in week five.
          
      
        
      
      
      
    
      
  
      

      



      
  
      
    
      
      05 / Control
      
      Four gates. Approval never carries forward.
      
      
      
        A gate is approved by a human, in that session, in response to named artifacts. An
        approval given for one version of a plan does not survive a change to it, and a passing
        test suite is never authorisation to ship.
      
      
    
      

    
      
      
      
        GATE 1
        
      Plan
      
        
      After the challenger has attacked the analysis. You see the root cause, the plan, and everything it could not verify.
      
        
      Blocks: any edit to a source file
      
      
      
      
      
        GATE 2
        
      Implementation
      
        
      The diff, and a self check against the plan. Scope drift is reported here rather than discovered at review.
      
        
      Blocks: the QA stage
      
      
      
      
      
        GATE 3
        
      QA
      
        
      Test evidence, code review, security findings, and the residual risk stated plainly. You accept evidence, not a claim.
      
        
      Blocks: the delivery gate
      
      
      
      
      
        GATE 4
        
      Delivery
      
        
      The exact branch name, commit message, PR body and Jira comment, before any of it happens.
      
        
      Blocks: every outward facing action
      
      
      
    
      

    
      
      
      
        
      What Sequent will not do
      
        
        
          
      • Merge a pull request.
        • 
          
      • Push to your default branch, or force push anywhere.
        • 
          
      • Post to Jira, push, or open a PR before Gate 4 is approved.
        • 
          
      • Weaken an assertion or skip a test to turn a suite green.
        • 
          
      • Report a check as passed when it was blocked.
        • 
        
      
      
      
      
      
        
      Why the gates are the product
      
        
      
          Delivery is a separate agent that verifies it was explicitly told Gate 4 was approved,
          in that invocation. It will not act on "QA passed" or "the reviewer approved".
        
      
        
      
          Every other agent's caution is wasted if the one that touches the outside world is
          casual about it. So that agent is the strictest one in the system.

      07 / The record
      
      Built to survive an audit, not just a demo
      
      
      
        Artifacts are written to disk as the run happens, so a closed terminal loses nothing.
        One command turns them into a single self contained HTML file you can send to whoever
        asks why a change was safe.
      
      
    
      

    
      
      
      
        01
        
      Agents propose, humans approve
      
        
      No production impacting change happens without a named person authorising it in that session. Not a policy we ask agents to respect, a gate they cannot pass.
      
      
      
      
      
        02
        
      Stage artifacts
      
        
      Analysis, challenge, implementation, QA, review, security, docs, release, retro. Each a readable document, not a log.
      
      
      
      
      
        03
        
      Event and tool trace
      
        
      Append only. Every stage transition and material tool call, with why it was made, how long it took, whether it worked. Secrets never enter it.
      
      
      
      
      
        04
        
      Scoped permissions
      
        
      Agents authenticate as their own identity with the narrowest access that does the job. What an agent may reach is your decision, and revocable.
      
      
      
      
      
        05
        
      Evidence for compliance
      
        
      The record maps onto what auditors actually ask for: who approved what, on what basis, and what was verified before it shipped.
      
      
      
      
      
        06
        
      Your boundary
      
        
      Runs on your infrastructure against your repositories. Where data must not leave, agents point at a model deployment inside your own tenancy.

      08 / Engineering standards
      
      What we build to, and what we will not claim
      
      
      
        Confidently wrong, drifting between runs, talked into things by their own input. Here is what we hold against that, and where each one stops.
      
      
    
      

    
      
      
      
        
      Traceability
      
        
      
          Every step recorded as it happens, each artifact linked to the step that produced it, append only so nothing rewrites history.
        
      
        
      
          Emitted as OpenTelemetry, so runs land in your telemetry and not a tool only we can read.
        
      
      
      

      
      
        
      Evaluation, including model as judge
      
        
      
          A test passing can be asserted. Whether an analysis is grounded in the files it cites cannot, so a separate model grades it against a rubric. We grade the trajectory too: a right answer reached recklessly is a problem that has not surfaced yet.
        
      
        
      
          The limit. Judges favour whichever option came first, output resembling their
          own, and longer answers. So: randomised ordering, rubrics written before the run, a
          second model from another family, agreement measured as Cohen's kappa. A judge is a
          signal, never the last word.
        
      
      
      

      
      
        
      Reproducibility
      
        
      
          Model, prompt and tool versions pinned and recorded. Inputs kept, so a run is replayed rather than re-argued.
        
      
        
      
          The limit. These systems are not deterministic. The commitment is that variation is attributable, not absent.
        
      
      
      

      
      
        
      Least privilege, and untrusted input
      
        
      
          The one that reads code cannot deploy. The one that opens a change cannot merge it. Anything arriving from outside is data to examine, never instruction to follow, which is the whole shape of indirect prompt injection.
        
      
        
      
          Built against the OWASP Top 10 for LLM Applications, and the Agentic list layered on top for risks that only appear once a system acts.
        
      
      
      

      
      
        
      Behavioural limits enforced outside the model
      
        
      
          A rule that lives only in a prompt is a suggestion. No merge, no force push, no protected branch, nothing outward before approval, all enforced by credentials and code path. A model that tried would fail, not succeed quietly.
        
      
        
      
          Budgets and stage caps, so a looping run stops on a limit rather than spending until somebody notices.
        
      
      
      

      
      
        
      Human oversight, and the evidence for it
      
        
      
          Recorded with the approver and their reasoning, and it never carries forward. A passing test suite is not authorisation to ship. Blocked checks are reported as loudly as passes.
        
      
        
      
          ISO/IEC 42001, the NIST AI Risk Management Framework and the EU AI Act are satisfied with evidence, and the run record is the evidence. We are not a certification and will not sign your conformity assessment.
        
      
      
      
    
      

    
      
      
      Why the caveats are on this page
      
      
      
        
      
          Every vendor says observable, evaluated and safe. Almost none says that judges are biased toward their own output, that runs are not strictly reproducible, or that a rule in a prompt is not a control.
        
      
        
      
          Better you hear the limits here than find them in month four. If one matters and we have not built it your way, that is the diagnostic week.

      10 / Where this sits
      
      Four levels of AI in engineering
      
      
      
        Each level is genuinely useful and each has a ceiling. Knowing which one you are at tells
        you what your next increment is actually worth.
      
      
    
      

    
      
      
      
        L1
        
      Chat assistants
      A conversational tool in a browser tab. Helpful for drafting and explaining. No contact with your delivery process.
      
        Individual
      
      
      
      
        L2
        
      Coding assistants
      Completion and suggestion inside the editor. Real gains on typing speed. Work still queues behind the same people in the same order.
      
        Most teams today
      
      
      
      
        L3
        
      Single purpose agents
      An agent that writes tests, triages a queue, or reviews a diff. Each works. None hand off to each other, so a person is still the integration layer.
      
        Early adopters
      
      
      
      
        L4
        
      Orchestrated delivery
      Specialist agents carrying a whole unit of work between them, with named human gates at the decisions that matter and an auditable record of every run. This is Sequent.
      
        Where we work
      
      
    
      

    
      
      L4 does not mean unattended. The gates are the point. A system that ships without a human
      is not a higher level, it is a different and worse risk profile.
